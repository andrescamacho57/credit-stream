# Snowflake Reference

Running reference for Snowflake on this project. Appended to as we go.

---

## What Snowflake Is

A cloud data warehouse. Its defining architectural choice: **storage and compute are
separated.** Data sits in cloud object storage; compute clusters ("warehouses") are
spun up to query it and can be resized or suspended independently.

**Why that matters:** you pay for compute only while it runs, multiple teams can
query the same data with separate compute so they don't slow each other down, and
scaling up is a config change rather than a migration.

## Object Hierarchy

```
Account
└── Database
    └── Schema
        ├── Tables
        ├── Views
        ├── Stages
        ├── File formats
        ├── Streams
        └── Tasks
```

**Account-level objects** (outside any database): warehouses, roles, users, storage
integrations.

**Schema-level objects** (inside a database.schema): tables, views, stages, file
formats.

**Fully qualified name:** `database.schema.object` —
`credit_stream.raw.accepted_loans`.

---

## Warehouses (Compute)

A **warehouse** is a compute cluster. It has nothing to do with storing data —
confusing name, but that's the term.

| Size | Relative cost/speed |
|---|---|
| X-Small | 1 credit/hour |
| Small | 2 |
| Medium | 4 |
| Large | 8 |

Each step up doubles both cost and compute. Warehouses auto-suspend when idle and
auto-resume on the next query — that's how a trial account doesn't burn credits
overnight.

**Bigger is not always faster.** If the work can't be split across threads — a
single gzip file, for example — extra compute sits idle. See the parallelism notes
in `CONCEPTS.md`.

## SQL Commands Used

### Context

```sql
USE ROLE ACCOUNTADMIN;
USE DATABASE credit_stream;
USE SCHEMA raw;
USE WAREHOUSE compute_wh;

SELECT CURRENT_REGION();      -- which cloud + region this account lives in
SELECT CURRENT_ACCOUNT();
SELECT CURRENT_ROLE();
```

### Inspecting
```sql
SHOW DATABASES;
SHOW SCHEMAS IN DATABASE credit_stream;
SHOW TABLES IN SCHEMA credit_stream.raw;
SHOW STAGES;
SHOW FILE FORMATS;
SHOW INTEGRATIONS;

DESC TABLE credit_stream.raw.accepted_loans;   -- column list
DESC INTEGRATION credit_stream_s3_int;         -- properties incl. generated values
```

**`DESC INTEGRATION` is how you retrieve the values AWS needs** —
`STORAGE_AWS_IAM_USER_ARN` and `STORAGE_AWS_EXTERNAL_ID` are generated by Snowflake
at creation time.

### Storage integration
```sql
CREATE STORAGE INTEGRATION credit_stream_s3_int
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::<account>:role/<role>'
  STORAGE_ALLOWED_LOCATIONS = ('s3://bucket-name/');
```

Account-level. Holds no credentials — auth is delegated to the AWS role's trust
policy. `STORAGE_ALLOWED_LOCATIONS` whitelists buckets so no stage using this
integration can point elsewhere.

### Stage
```sql
CREATE STAGE credit_stream.raw.s3_raw_stage
  URL = 's3://bucket-name/'
  STORAGE_INTEGRATION = credit_stream_s3_int;

LIST @credit_stream.raw.s3_raw_stage;
LIST @credit_stream.raw.s3_raw_stage/raw/lending_club/;
```

**The `@` marks a stage reference.** Without it Snowflake reads the name as a table.
Forms: `@my_stage` (named), `@~` (user stage), `@%my_table` (table stage).

**`LIST` exercises `ListBucket` only, not `GetObject`** — a successful `LIST` does
not prove you can read file contents.

### File format
```sql
CREATE OR REPLACE FILE FORMAT credit_stream.raw.ff_lending_club_csv
  TYPE = CSV
  SKIP_HEADER = 1
  FIELD_OPTIONALLY_ENCLOSED_BY = '"'
  COMPRESSION = AUTO
  NULL_IF = ('', 'NULL', 'null', 'n/a')
  EMPTY_FIELD_AS_NULL = TRUE;
```

Snowflake receives bytes and has no idea they're a table. The file format is the
decoder: where a row ends, what separates fields, whether row one is a header,
whether the bytes are compressed.

**`FIELD_OPTIONALLY_ENCLOSED_BY = '"'` is the setting that saves you.** Free-text
columns contain commas and newlines; CSV convention wraps those fields in double
quotes so the commas inside are data, not delimiters. Snowflake only honors that if
told to. **This is the most common cause of CSV load failure.**

### Loading
```sql
COPY INTO credit_stream.raw.accepted_loans
FROM @credit_stream.raw.s3_raw_stage/raw/lending_club/
FILE_FORMAT = (FORMAT_NAME = credit_stream.raw.ff_lending_club_csv)
ON_ERROR = 'ABORT_STATEMENT';
```

**`ON_ERROR` options:**
| Value | Behavior |
|---|---|
| `ABORT_STATEMENT` | First bad row kills the load. Nothing written. **Default choice.** |
| `CONTINUE` | Skip bad rows, load the rest. Silently discards data. |
| `SKIP_FILE` | Abandon that file, continue with others. |

**Fail loud first, decide tolerance second.** `CONTINUE` on a first load hides how
much you lost and why.

**`VALIDATION_MODE = 'RETURN_ERRORS'`** dry-runs a load and reports problems without
writing anything. Worth it for expensive loads.

**Pointing at a prefix rather than a filename** (`.../lending_club/` not
`.../file.csv.gz`) means future files under that path get picked up by the same
statement.

## Gotchas

**Reserved keywords need double quotes.** `DESC` is short for DESCRIBE and is also
the `ORDER BY` sort direction, so a column named `desc` must be written `"DESC"`.
Same problem with `order`, `group`, `case`, `end`, `select`.

**Snowflake uppercases unquoted identifiers.** `accepted_loans` becomes
`ACCEPTED_LOANS` internally. Quoting an identifier makes it case-sensitive forever —
which is why `"desc"` and `"DESC"` are different columns. Avoid quoting unless you
must.

**A clean `COPY` result does not prove correctness.** `rows_loaded` means nothing
choked. A misparse can shift every column one position right and still report
success. **Always validate after loading:**

```sql
-- grain check
SELECT COUNT(*) AS total_rows, COUNT(DISTINCT id) AS distinct_ids
FROM credit_stream.raw.accepted_loans;

-- eyeball column alignment
SELECT id, loan_amnt, term, purpose FROM ... LIMIT 5;
```

Cross-check the row count against something you measured independently —
`wc -l` on the source file minus the header.

**Account region is fixed at creation.** Cannot be changed later.

## Load History & Debugging

```sql
-- what loads have run against this table
SELECT *
FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'credit_stream.raw.accepted_loans',
  START_TIME => DATEADD(hours, -24, CURRENT_TIMESTAMP())
));

-- query history
SELECT query_text, execution_status, total_elapsed_time
FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY())
ORDER BY start_time DESC
LIMIT 20;
```

**Snowflake tracks which files it has already loaded** into a table and skips them
on subsequent `COPY INTO` runs by default. That's how re-running a load doesn't
duplicate data. `FORCE = TRUE` overrides it.

## CLI Tools (not installed yet)

Two separate programs, easily confused:

**`snow`** — the modern Snowflake CLI. Manages connections, runs SQL files, deploys
objects, handles Snowpark. This is the current one.

**`snowsql`** — the older SQL-focused CLI. Being superseded by `snow`.

Expected usage once installed:
```bash
snow --version
snow connection list
snow connection add
snow sql -f snowflake/01_setup.sql        # run a file
snow sql -q "SELECT CURRENT_REGION()"     # run a query
```

**Why a CLI matters later:** CI pipelines and orchestrators run SQL files
non-interactively. A browser worksheet can't do that.

**Currently using instead:** the VS Code Snowflake extension — the file that runs is
the file in Git, so there's no drift between version control and what executed.

## Authentication

### The deprecation timeline (why this matters now)

Snowflake is eliminating single-factor password sign-ins in three milestones:

| Window | Change |
|---|---|
| Sept 2025 – Jan 2026 | MFA required for Snowsight logins using passwords |
| **May 2026 – Jul 2026** | All **newly created** human users must use MFA |
| **Aug 2026 – Oct 2026** | All human users must use MFA; all service users must use key pair, OAuth, PAT, or workload identity |

Trial accounts are generally exempt until converted to paid — but that's a moving
target, not a foundation.

**The decisive argument is CI: a GitHub Actions runner cannot type an MFA code.**
Key pair authentication exists for exactly this. Any automated pipeline needs it.

### User types
| TYPE | Meaning |
|---|---|
| `null` / `PERSON` | Human. Will require MFA for password auth. |
| `SERVICE` | Automation. Cannot use passwords at all — key pair / OAuth only. |
| `LEGACY_SERVICE` | Transitional, being removed. |

**Don't set `TYPE = SERVICE` on your own login** — it blocks web UI access. A human
user can hold an RSA public key and use both: password+MFA in the browser, key pair
for tooling. Separate service users are what a real team creates for CI.

### Registering a public key
```sql
SELECT CURRENT_USER();

ALTER USER AFCAMACH SET RSA_PUBLIC_KEY = 'MIIBIjANBgkqh...';

DESC USER AFCAMACH;
```

The key goes in as **one unbroken string** with the `-----BEGIN/END-----` wrapper
lines stripped and newlines removed:
```bash
grep -v "^-----" ~/.snowflake/rsa_key.pub | tr -d '\n' | pbcopy
```

**Verify via `DESC USER`:**
- `RSA_PUBLIC_KEY_FP` — the fingerprint. If populated, Snowflake accepted the key.
- `RSA_PUBLIC_KEY_LAST_SET_TIME` — timestamp of registration.

Snowflake displays the fingerprint rather than the key because a fingerprint is short
enough to eyeball when comparing keys. The public key itself isn't secret.

**Snowflake supports two keys** (`RSA_PUBLIC_KEY` and `RSA_PUBLIC_KEY_2`) so you can
rotate without downtime: register the new one, switch clients over, then remove the
old.

### Key generation
See `UNIX_COMMANDS.md` for the `openssl` commands. Snowflake requires **PKCS#8**
format for the private key.

**`ALTER USER ... SET RSA_PUBLIC_KEY` does not belong in version control.** The key
is specific to one machine — anyone cloning the repo generates their own. It's a
procedure to document in the README, not code to commit.

## SQL Patterns Used In This Project

### Validating a load

```sql
-- count(*) counts rows; count(col) counts NON-NULL values.
-- The gap between them is the null count, no WHERE needed.
select
    count(*)              as total_rows,
    count(loan_amnt)      as amount_populated,
    count(emp_length)     as emp_length_populated
from credit_stream.raw.accepted_loans;
```

Run the same shape against the source and the transformed model, then compare column
by column. Matching numbers mean the transformation destroyed nothing. A gap separates
"already null in the source" from "my cast silently broke it."

### count_if

```sql
select
    count_if(try_cast(id as number) is null)  as non_numeric_id,
    count_if(loan_amnt is null)               as null_amount
from credit_stream.raw.accepted_loans;
```

Counts rows where a condition is true. Cleaner than
`sum(case when ... then 1 else 0 end)`.

**Use it to measure a filter's blast radius before applying it.** If the count differs
from what you expect to remove, there is a category of data you have not looked at.

### Percentage of total with a window function

```sql
select
    purpose,
    count(*)                                            as loan_count,
    round(100.0 * count(*) / sum(count(*)) over (), 2)  as pct_of_loans
from credit_stream.dbt_andres.stg_loans
group by purpose
order by loan_count desc;
```

`sum(count(*)) over ()` is a window over the entire result set — it puts the grand
total on every row, so you get a percentage without a second pass.

### Finding orphans (anti-join)

```sql
select l.state_code, count(*) as loan_count
from credit_stream.dbt_andres.stg_loans l
left join credit_stream.dbt_andres.dim_geography g
    on l.state_code = g.state_key
where g.state_key is null
group by l.state_code;
```

**Left join, then filter for nulls on the right.** Finds rows in the left table with no
match. The standard "what is missing" query — and the mechanism behind dbt's
`relationships` test.

### Column metadata from the catalog

```sql
select count(*) as column_count
from credit_stream.information_schema.columns
where table_schema = 'DBT_ANDRES'
  and table_name = 'STG_LOANS';
```

`information_schema` is the authoritative source for structure. Better than counting
lines in a SQL file with `grep`, which also matches comments and CTE definitions.

## Useful Functions

| Function | Does |
|---|---|
| `try_cast(x as type)` | cast, returning null instead of erroring |
| `try_to_date(x, 'MON-YYYY')` | parse a date, null on failure |
| `regexp_substr(term, '[0-9]+')` | first run of digits — `" 36 months"` → `"36"` |
| `split_part(s, 'Status:', 2)` | split on a delimiter, take the Nth piece |
| `initcap(replace(s, '_', ' '))` | `debt_consolidation` → `Debt Consolidation` |
| `to_char(d, 'YYYYMMDD')` | date → string, for building integer date keys |
| `date_trunc('month', d)` | first day of the month |
| `last_day(d, 'month')` | last day of the month |
| `dayofweek` / `dayname` / `monthname` / `weekofyear` | date parts |

**`try_cast` fails silently** — it can null out a whole column and still report success.
Pair permissive casting with a null-count check and a `not_null` test.

## Snowflake Notes Learned The Hard Way

**A DATE is stored internally as an integer** (days since an epoch). Joining on a date
column is an integer comparison, not string matching. So "integer date keys are faster"
is not the real argument for `YYYYMMDD` — convention and readability are.

**`show tables in credit_stream;` fails** — `SHOW TABLES IN` needs a schema, or use
`SHOW TABLES IN DATABASE credit_stream`.

**Diagnostics do not belong in setup scripts.** `SELECT CURRENT_REGION()` and
`DESC INTEGRATION` answer questions; they do not create state. Keeping them in a
numbered setup file makes it unclear what is essential.
